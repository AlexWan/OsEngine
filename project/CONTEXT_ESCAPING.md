# CONTEXT_ESCAPING — наборы экранирования по носителям сериализации

> Политика: что и как экранировать в носителях построчной сериализации. Читать перед правкой
> `GetStringForSave` / `GetStringFofSave` / `GetSaveString` / `Set*FromString` и перед созданием
> нового построчного формата.
> Проверено по commit e33e66d9 и веткам `fix/bug-0446`, `fix/bug-0450`, `fix/bug-0453`,
> `fix/bug-0457` (PR 2153, 2154, 2155), дата проверки: 2026-11-17.

## 1. Назначение и область

Носители OsEngine построчные: записи разделены CR/LF, поля — разделителем носителя, внутрь поля
может быть вложена строка другого носителя со своим разделителем. Значение с сырым разделителем
ломает запись (сдвиг полей), с CR/LF — разрывает запись пополам. Три фикса одного класса
(Bug 0446 / 0450 / 0453) ввели разные наборы — здесь зафиксировано, почему наборы различны, какой
носитель чем защищён, где остались легаси и разрывы.

Политика покрывает построчные форматы. JSON (MCP) и санитайзер имён файлов вне политики — они
включены в таблицу, чтобы их не путали с экранированием носителей.

## 2. Канон (для всех новых line-based носителей)

1. Экранирование обратимое, вид `%XX`. Деструктивный стрип `Replace("<символ>", "")` как защита
   запрещён: значение теряется, загрузка его не восстанавливает.
2. Знак экранирования — `%`. При сохранении `%` экранируется первым (`%`→`%25`), при загрузке
   `%25` декодируется последним — иначе последовательности, порождённые самим экранированием,
   декодируются второй раз.
3. Набор = союз разделителей всех уровней вложенности записи значения + `CR` + `LF` + `%`.
   Для каждого символа набора указывай уровень вложенности, который его требует, — иначе
   «союз уровней» нельзя проверить при ревью.
4. Экранирует уровень, владеющий значением, непосредственно перед склейкой с разделителем.
5. Round-trip обязан восстанавливать значение побайтово.
6. Значение, переходящее между носителями, экранируется набором того носителя, в которое сейчас
   пишется. Носители с легаси-исключениями (§4) не место для хранения уже экранированного
   значения: двойное экранирование раскроется неверно.

## 4. Легаси-исключения (четыре, два исчерпаны)

1. **MyTrade `SecurityNameCode`** — исчерпано (fix/bug-0457). Было: save `Replace("@","%")`
   (MyTrade.cs:76), load `Replace('%','@')` (MyTrade.cs:95) — lossy. Стало: save — `EscapingId`
   (канон §2, голый `%` в файл не пишется); load — `UnescapingIdLegacy`: голый `%`, не начинающий
   последовательность канона (`%25/%40/%23/%5E/%2A/%26/%0D/%0A`), читается как `@` — старые журналы
   легаси-хака остаются читаемыми. Новый читатель тождественен старому для legacy-значений БЕЗ `%`
   перед hex-префиксом набора кодировщика; неоднозначные — в пользу канона. Не гарантируем: литералы `%0D`/`%0A`
   в значениях декодируются в CR/LF, но структурно безопасны (декод идёт по полям после split,
   повторный save экранирует обратно); структурно опасен сырой CR/LF в legacy-поле — это хвост
   `SecurityName` §4.3, зона BUG-0458, fallback его не лечит. Принятые
   characterization-потери: коллизионный класс (как в PR 2154) — не «начинающиеся», а старые
   значения, СОДЕРЖАЩИЕ `%` непосредственно перед hex-префиксом набора в любой позиции, декодируются
   как escape; смешанный класс `%%40` — было `@@40`, стало `@@`; асимметрия MyTrade `%2A` — было
   `@2A`, стало `*` (`2A` в lookahead MyTrade, нет в наборе Order); lowercase-hex в legacy
   (`%5e`, `%2a`) — разворот в `@` тождественно старому читателю (lookahead только верхний регистр).
   Null: save `SecurityNameCode = null` на master бросал NRE (:76 без гейта; у Order — :508), фикс
   УБИРАЕТ ПАДЕНИЕ (улучшение, а не сохранение байтов): null пишется и читается как `""`.
   Несогласованность null-контрактов декодеров зафиксирована как есть: `UnescapeFieldLegacy(null)` →
   `null` против `UnescapingId(null)` → `""` (загрузкам приходит результат `Split`, не null;
   при надобности пинится тестом, код не выравнивается).
2. **Order `SecurityNameCode` / `PortfolioNumber`** — исчерпано (fix/bug-0457). Было: save
   `Replace('@','%')` (Order.cs:508, :512), load `Replace('%','@')` (Order.cs:592, :593). Стало:
   save — `EscapeField` (канон §2); load — `UnescapeFieldLegacy` (fallback по набору
   `%25/%40/%23/%5E/%0D/%0A`). Тождественность старому читателю и characterization-потери — как
   §4.1, с различием: `%2A` для Order не потеря (`2A` не в наборе) — читается тождественно старому.
   Null: `PortfolioNumber` на master имел null-гейт (master :510–:517) — save побайтово тот же;
   `SecurityNameCode = null` — NRE, убран фиксом (§4.1).
3. **Стрип коммент-блока журнала позиций**:
   `RemoveExcessFromSecurityName().Replace("#","").Replace("^","")` применяется к Comment
   (Position.cs:1411), SignalTypeStop (:1418), SignalTypeProfit (:1428), SignalTypeOpen (:1468),
   SignalTypeClose (:1475) и мутирует живые свойства позиции. `SecurityName` под стрип не попадает —
   экранирован в хвосте записи (fix/bug-0458, §3).
4. **`RemoveExcessFromSecurityName` (Extensions.cs:20)** — санитайзер имён файлов (вырезает
   `/ \ * : @ ; ` и кавычку), НЕ сериализационное экранирование. Не применять его как защиту
   носителя и не расширять его набор для этой цели.

## 5. Известные разрывы

Статус строки «журнал позиций» в таблице — «частично защищён», не «экранирован»: хвост
SecurityName экранирован с fix/bug-0458 (ранее литерный `#` в имени резал значение при загрузке —
BUG-0458; легаси-записи с сырым `#` читаются сканом bool-пары, §3); все пять стрип-полей
коммент-блока защищены идентично и деструктивно (lossy). Семейство стрипа заведено тикетом BUG-0452:

- `Comment` (Position.cs:1411) — BUG-0452; fix/bug-0446 (PR 2153) добавил только замену CR/LF на
  пробел; `#` и `^` по-прежнему вырезаются деструктивно. Обратимый `EscapeField` покрывает поле
  Comment внутри строки Order, а не коммент-блок записи позиции.
- `SignalTypeStop` (Position.cs:1418), `SignalTypeProfit` (Position.cs:1428) — BUG-0452; стрип
  идентичен Comment, значения теряются.
- `SignalTypeOpen` (Position.cs:1468), `SignalTypeClose` (Position.cs:1475) — BUG-0452; тот же
  lossy-стрип, обратимого экранирования нет.

Прочие разрывы:

- BUG-0457 — закрыт (fix/bug-0457): `MyTrade.SecurityNameCode` и `SecurityNameCode` /
  `PortfolioNumber` строки Order экранированы по канону §2; чтение старых журналов —
  legacy-fallback §4.1/§4.2.

Разрывы заведены тикетами (BUG-0452, BUG-0457 — закрыт); этот документ их фиксирует и не чинит.
BUG-0458 (сырой `SecurityName` в хвосте) исправлен в PR ветки `fix/bug-0458` и из списка снят.

**Политика: даунгрейд не поддерживается** (P3, fix/bug-0457). Файл нового формата, прочитанный
старым билдом, декодируется ложно: канон-последовательности разворачиваются в сторону голого
`%`→`@` (`%40` → `@40`, `%25` → `@25`); структура записей цела (`@`/CR/LF не пишутся сырыми;
`&` и `*` безопасны в полях Order — разделители только в MyTrade-сегменте), искажаются значения;
повторный save старым билдом фиксирует
искажение в файле. Рекомендация: перед апгрейдом делать бэкап журнала. Ограничение (поведение
master, фиксом не изменено): первый save нового билда переписывает журнал целиком, бэкапа нет.

## 6. Процедура поддержки

1. Изменяешь существующий носитель — обнови его строку в §3: набор, кодировщик/декодер, статус,
   дату проверки.
2. Создаёшь новый построчный формат — заведи строку в §3 до мержа PR: носитель, разделители по
   уровням, набор с выводимостью каждого символа (§2.3), кодировщик, дата. Набор — из канона §2.
3. PR с новым или изменённым построчным форматом без обновления этого документа — нарушение
   политики, ревью не проходит. То же для PR, которые приносят пользовательский или брокерский
   текст в носитель со статусом «вне политики».
4. Новый код следует канону §2; легаси-исключения §4 не воспроизводить в новом коде.
