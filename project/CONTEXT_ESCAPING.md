# CONTEXT_ESCAPING — наборы экранирования по носителям сериализации

> Политика: что и как экранировать в носителях построчной сериализации. Читать перед правкой
> `GetStringForSave` / `GetStringFofSave` / `GetSaveString` / `Set*FromString` и перед созданием
> нового построчного формата.
> Проверено по commit e33e66d9 и веткам `fix/bug-0446`, `fix/bug-0450`, `fix/bug-0453`
> (PR 2153, 2154, 2155), дата проверки: 2026-11-16.

## 1. Назначение и область

Носители OsEngine построчные: записи разделены CR/LF, поля — разделителем носителя, внутрь поля
может быть вложена строка другого носителя со своим разделителем. Значение с сырым разделителем
ломает запись (сдвиг полей), с CR/LF — разрывает запись пополам. Три фикса одного класса
(Bug 0446 / 0450 / 0453) ввели разные наборы — здесь зафиксировано, почему наборы различны, какой
носитель чем защищён, где остались легаси и разрывы.

Политика покрывает построчные форматы. JSON (MCP) и санитайзер имён файлов вне политики — они
включены в таблицу, чтобы их не путали с экранированием носителей.

## 2. Канон (для всех новых line-based носителей)

1. Экранирование обратимое, вид `%XX`. Деструктивный стрип `Replace("<символ>", "")` как защита
   запрещён: значение теряется, загрузка его не восстанавливает.
2. Знак экранирования — `%`. При сохранении `%` экранируется первым (`%`→`%25`), при загрузке
   `%25` декодируется последним — иначе последовательности, порождённые самим экранированием,
   декодируются второй раз.
3. Набор = союз разделителей всех уровней вложенности записи значения + `CR` + `LF` + `%`.
   Для каждого символа набора указывай уровень вложенности, который его требует, — иначе
   «союз уровней» нельзя проверить при ревью.
4. Экранирует уровень, владеющий значением, непосредственно перед склейкой с разделителем.
5. Round-trip обязан восстанавливать значение побайтово.
6. Значение, переходящее между носителями, экранируется набором того носителя, в которое сейчас
   пишется. Носители с легаси-исключениями (§4) не место для хранения уже экранированного
   значения: двойное экранирование раскроется неверно.

## 4. Легаси-исключения (четыре, явно)

1. **MyTrade `SecurityNameCode`**: save `Replace("@","%")` (MyTrade.cs:76), load
   `Replace('%','@')` (MyTrade.cs:95). Асимметрично и lossy: литерный `%` в значении декодируется
   как `@` (ложное декодирование); сам `%` не экранируется.
2. **Order `SecurityNameCode` / `PortfolioNumber`**: save `Replace('@','%')` (Order.cs:508, :512),
   load `Replace('%','@')` (Order.cs:592, :593). Тот же ложный разворот литерного `%` в `@`.
3. **Стрип коммент-блока журнала позиций и хвост SecurityName**:
   `RemoveExcessFromSecurityName().Replace("#","").Replace("^","")` применяется к Comment
   (Position.cs:1411), SignalTypeStop (:1418), SignalTypeProfit (:1428), SignalTypeOpen (:1468),
   SignalTypeClose (:1475) и мутирует живые свойства позиции; `SecurityName` дописан сырым в хвост
   записи (:1497), загрузчик читает его как `arraySave[arraySave.Length - 1]` (:1657) — литерный
   `#` в названии (MOEX ISS формат `Class#Board`) обрезает значение при загрузке.
4. **`RemoveExcessFromSecurityName` (Extensions.cs:20)** — санитайзер имён файлов (вырезает
   `/ \ * : @ ; ` и кавычку), НЕ сериализационное экранирование. Не применять его как защиту
   носителя и не расширять его набор для этой цели.

## 5. Известные разрывы

Статус строки «журнал позиций» в таблице — «легаси-деструктивный», не «экранирован»: все пять
стрип-полей коммент-блока защищены идентично и деструктивно (lossy). Семейство стрипа заведено
тикетом BUG-0452:

- `Comment` (Position.cs:1411) — BUG-0452; fix/bug-0446 (PR 2153) добавил только замену CR/LF на
  пробел; `#` и `^` по-прежнему вырезаются деструктивно. Обратимый `CommentEscape` покрывает поле
  Comment внутри строки Order, а не коммент-блок записи позиции.
- `SignalTypeStop` (Position.cs:1418), `SignalTypeProfit` (Position.cs:1428) — BUG-0452; стрип
  идентичен Comment, значения теряются.
- `SignalTypeOpen` (Position.cs:1468), `SignalTypeClose` (Position.cs:1475) — BUG-0452; тот же
  lossy-стрип, обратимого экранирования нет.

Прочие разрывы:

- BUG-0457 — `MyTrade.SecurityNameCode` остался легаси-хаком `@`→`%` после PR 2154 (§4.1):
  брокерский текст с `%` будет ложно развёрнут в `@`.
- BUG-0458 — сырой `SecurityName` в хвосте записи позиции (§4.3): литерный `#` в названии бумаги
  (MOEX ISS формат `Class#Board`) обрезает значение при загрузке журнала.

Каждый разрыв заведён тикетом (BUG-0452, BUG-0457, BUG-0458); этот документ их фиксирует и не
чинит.

## 6. Процедура поддержки

1. Изменяешь существующий носитель — обнови его строку в §3: набор, кодировщик/декодер, статус,
   дату проверки.
2. Создаёшь новый построчный формат — заведи строку в §3 до мержа PR: носитель, разделители по
   уровням, набор с выводимостью каждого символа (§2.3), кодировщик, дата. Набор — из канона §2.
3. PR с новым или изменённым построчным форматом без обновления этого документа — нарушение
   политики, ревью не проходит. То же для PR, которые приносят пользовательский или брокерский
   текст в носитель со статусом «вне политики».
4. Новый код следует канону §2; легаси-исключения §4 не воспроизводить в новом коде.
