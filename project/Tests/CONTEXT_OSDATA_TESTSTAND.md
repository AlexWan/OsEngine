# CONTEXT_OSDATA_TESTSTAND — тестовый стенд OsData (консольная программа)

> Описание тестового стенда `OsEngine.OsData.TestStand` — детерминированная проверка данных OsData
> (бумаги, свечи, тики, стаканы) через MCP OsEngine. Стенд доступен внешним агентам
> для штатного теста коннектора и точечной проверки конкретной бумаги.
>
> По образцу этого стенда построен стенд тестера `OsEngine.OsTester.TestStand`
> (см. [`CONTEXT_OSTESTER_TESTSTAND.md`](CONTEXT_OSTESTER_TESTSTAND.md)).

## 1. Цель

Дать внешним агентам готовый инструмент для проверки OsData-коннектора, чтобы агент
**не выдумывал проверки заново** на каждом запуске, а:
1) запускал стенд для конкретного коннектора;
2) получал структурированный отчёт pass/fail по проверкам;
3) интерпретировал результат и отчитывался / эскалировал.

## 2. Расположение и имя

- Путь: `project\Tests\OsDataTestStand\OsEngine.OsData.TestStand\`.
- Имя проекта: `OsEngine.OsData.TestStand` (`.csproj`, `net10.0`, консоль).
- Работает только через MCP OsEngine — **без прямой ссылки на OsEngine**.

## 3. Как устроен

- `Program.cs` — вход: лог-файл, консольное окно, парсинг аргументов, перебор модулей через `RunModule`
  (каждый модуль перезапускает OsEngine перед собой и гасит после).
- `OsEngineProcessController.cs` — запуск/остановка OsEngine, ожидание MCP-порта.
- `McpApiClient.cs` — MCP-клиент (`ToolsCall`, V1/V2).
- `TestContext.cs` — отчётность (`RecordPass/RecordFail/PrintSummary`), маскирование секретов.
- `TestResult.cs` — pass/fail.
- `TestSecrets.cs` — ключи/токены (не в git).
- `Tests/OsDataTestsBase.cs` — общий поток модулей (открыть OsData, погасить сеты, выбрать представителей).
- `Tests/QshParser.cs` — парсер бинарных `.qsh` (стаканы, история/онлайн).
- `Tests/*.cs` — модули тестов (см. п. 4).

## 4. Модули (что проверяет)

### 4.1. Security (бумаги)

- **4.1.1.** В списке `server_instance_get_securities` нет дублей по имени/идентификатору.
- **4.1.2.** У каждой бумаги уникальный `name_id`.

### 4.2. Свечи (Candles)

По одному инструменту из каждого класса, период ~1 месяц, все доступные таймфреймы.

- **4.2.1. Загрузка.** Кол-во свечей в разных ТФ **различается**.
- **4.2.2. OHLC.** В каждой свече `high ≥ open`, `high ≥ close`, `low ≤ open`, `low ≤ close`, `high ≥ low`.
- **4.2.3. Дубли.** Нет одинаковых свечей (по времени).
- **4.2.4. Дыры.** На дневном ТФ нет пропусков больше выходных (gap > 4 дней).
- **4.2.5. Время.** Свечи в строго возрастающем порядке.
- **4.2.6. Выравнивание ТФ.** 90% соседних свечей отстоят ровно на шаг таймфрейма (ночной разрыв не считается ошибкой).

### 4.3. Тики (Ticks)

- **4.3.1. Загрузка.** Тиков > 0, цена > 0, объём > 0, сторона `Buy`/`Sell`.
- **4.3.2. Хронология.** Тики в строго возрастающем порядке (дата + микросекунды).
- **4.3.3. Дубли.** Нет одинаковых тиков (по цене/объёму/времени/id; допуск ≤ 10 — у некоторых коннекторов id генерируется).

### 4.4. Стаканы. История (только `QscalpMarketDepth`, без ключа/токена)

- **4.4.1. Файлы.** `.qsh`-файлы скачаны и непустые.
- **4.4.2. Валидность.** В каждом срезе `bid ≤ ask`, цены > 0, уровни упорядочены, объём на уровне ≠ 0.

### 4.5. Стаканы. Он-лайн (боевой коннектор, с токеном)

- **4.5.1. Получение.** Подписка даёт срезы стакана (bid/ask) для коннекторов с live depth
  (тестируется на `TInvest`). Токен — в `test-secrets.json`; без токена — ошибка.
  Инструменты без live-стакана (валюта/иностранные) в общем режиме пропускаются, в точечном — FAIL.

### 4.6. Нагрузка

- **4.6.1.** Сет из 10 инструментов (акции), проверить загрузку всех.
- **4.6.2.** Смешанные таймфреймы в одном сете (1m/5m/1h/1d).
- **4.6.3.** Повторное включение сета (off → on) без дублей.

## 5. Как запускать

```bash
dotnet run -- [--connector MoexDataServer] [--module/-m NAME] [--security TICKER] [--timeframes Min5,Day] [--from YYYY-MM-DD] [--to YYYY-MM-DD] [--no-wait]
```

Полные флаги: `--port`, `--api-key`, `--timeout`, `--transport v1|v2`, `--mode`, `--module/-m`,
`--connector`, `--security`, `--timeframes`, `--from`, `--to`, `--no-wait`.

### Обычный режим (по представителям)

Без `--security` каждый модуль тестирует по одному представителю из каждого класса бумаг
(валюта → `CNYRUB_TOM`, акции → `SBER`, ETF → `TMOS`, фьючерс → ближайший контракт).

### Точечный режим (одна конкретная бумага)

С `--security TICKER` модуль тестирует только эту бумагу вместо представителей:

- `--security` — тикер (обязателен для точечного режима);
- `--timeframes Min5,Day` — какие ТФ качать (для свечей; по умолчанию — все доступные);
- `--from` / `--to` — период, ISO `YYYY-MM-DD` (по умолчанию — дефолт модуля: свечи ~месяц, тики ~2 дня, стаканы история ~1 день);
- `--connector` — коннектор (по умолчанию `MoexDataServer`).

Работает во всех модулях данных (Candles, Ticks, MarketDepthHistory, MarketDepthOnline).

```bash
# Свечи SBER из Finam за март 2024
dotnet run -- -m Candles --connector Finam --security SBER --timeframes Min5,Day --from 2024-03-01 --to 2024-03-31

# Тики SBER из TDataHistory за период
dotnet run -- -m Ticks --connector TDataHistory --security SBER --from 2026-09-01 --to 2026-09-03

# Стаканы SBER из Qscalp за день
dotnet run -- -m MarketDepthHistory --connector QscalpMarketDepth --security SBER --from 2026-09-23 --to 2026-09-24
```

Бумага не найдена или по ней нет данных за период — **явный FAIL** (не тихий пропуск).

## 6. Что на выходе

Во время прогона — построчно `[Module N] ...` + `Status: PASS/FAIL - ...`. В конце — сводка:

```
--- Module Summary ---
CANDLES: 70/70 passed
...

Total: 70/70 passed in 332.1s

--- Protocol Violations ---
none
```

- `Total: X/Y passed` — главный итог; при `> 0` failed стенд завершается с **ненулевым кодом выхода**.
- `--- Protocol Violations ---` — отклонения от протокола MCP (заголовки/JSON-RPC/статус-коды), не считаются фейлом.
- Вывод дублируется в консоль + лог-файл `osdata-test-stand-yyyyMMdd-HHmmss.log` рядом с `.exe`.

## 7. Длительность

| Модуль | Ориентир |
|---|---|
| Security | ~1 мин |
| Candles | ~5–6 мин |
| Ticks | ~2–3 мин |
| MarketDepthHistory | ~2 мин |
| MarketDepthOnline | ~3 мин |
| Load | ~1–2 мин |

Основное время — перезапуск OsEngine перед каждым модулем, а не сами проверки.
Точечный режим (одна бумага) заметно быстрее общего.

## 8. Примечания

- Стенд работает через MCP OsEngine (`data_*`, `server_management_*`, `server_instance_*`, `terminal_*`) —
  тот же путь, что и у внешних агентов. Разница: проверки детерминированы и закодированы.
- Коннекторы по модулям: свечи — `MoexDataServer` (или любой свечной), тики — `TDataHistory`,
  стаканы история — `QscalpMarketDepth`, стаканы онлайн — `TInvest`.
- Ключи/токены — в `test-secrets.json` (не в git), по образцу `McpApi.TestStand`.
- Имена сетов стенда — с префиксом `TesterData_*` (папки `Set_TesterData_*`); чистятся после прогона,
  чтобы не путать с сетами внешних агентов.
- Парсер `.qsh` (`QshParser.cs`) переиспользуется в стаканах (история и онлайн).
